# Changelog

All notable changes to Plexo are documented here.
Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)

## [Unreleased]

- **Pull requests now have a gate that actually runs, so `verify` can be made required.** plexo had no check that fired on a PR: `ci.yml` is `push`-only, and the one PR-triggered workflow (`changelog-check.yml`) is path-filtered to `packages/sdk/**` and has never executed once — so requiring it would park every PR in "Waiting for status to be reported", permanently, with no self-approval escape for a solo maintainer. New `.github/workflows/pr-gate.yml` runs `on: pull_request` on `ubuntu-latest` and reports a single job named **`verify`**, matching nexalog and fonto so one identical required context covers all three public repos. It runs the portable subset of `ci.yml` verbatim — SDK build, `typecheck`, `arch:check`, `db:check-drift`, `test`, `test:unit` — every command copied from the existing job bodies.
- **Why the gate is a separate file rather than a trigger added to `ci.yml`.** This repo is public, and for a `pull_request` event GitHub resolves the workflow from the PR's *merge commit*, so a fork controls the job body including `runs-on`. `ci.yml`'s `docker-build` and `graphiti-sidecar` land on the `docker`-labelled runner, which is uid=0 with `/var/run/docker.sock` mounted rw — host-root-equivalent. Bolting a PR trigger onto that file would hand untrusted fork code a root shell on the host. Hosted runners contain fork code by design, and for public repos they are free and unlimited (the 2,000-minute allowance meters private repos only) at 4 vCPU / 16 GB. The file records this as an INVARIANT: never `pull_request_target`, never `self-hosted`, never a `secrets.*` dependency (fork PRs receive none, so one would fail every outside contribution) — which is also why `integration`, needing a long-lived CI Postgres/Redis and `CI_DATABASE_URL`, stays push-only in `ci.yml`.
- **`lint` is deliberately absent from the gate.** It is red on `main` today: `scripts/check-doc-refs.sh` reports 36 dead path references across `CLAUDE.md`, `AGENTS.md`, `README.md`, and `.claude/rules/*`, all citing a `docs/claude/` tree that does not exist. Requiring a failing check would block every PR, so the gate carries only the four checks that are green. Fixing the doc references is a separate content decision (create the promised files, or correct the citations) and once done `lint` should be added here. `ci.yml`'s `integration` job is separately red — `CI_DATABASE_URL` resolves empty so `psql` falls back to a nonexistent local socket.

- **Logo: closed triangle with differently-colored vertex dots.** The Delta-Frame triangle no longer breaks at the base, and its three endpoint dots are now distinct brand colors — accent blue (apex), signal green (left), amber (right). Applied to the web `PlexoMark`, the favicon, the Android launcher icons, the desktop `icon.svg`/`icon.png` + programmatic BGRA fallback + connect-screen glyph, and the Flutter `PlexoMark`. Web/desktop/mobile triangle edges follow the surrounding text color; only the dots are brand-fixed, so the mark reads on light and dark surfaces alike.
- **The mobile app is functional, not a placeholder shell.** `apps/mobile` shipped as a Phase-0 skeleton — four of its five tabs rendered "Coming in a later phase". It now talks to the real API: **Chat** sends `POST /api/v1/chat/message` and renders whichever terminal shape returns (a direct reply, a queued task polled via `GET /api/v1/chat/reply/:taskId`, a PROJECT confirm that calls `POST /api/v1/chat/execute-action`, or a soft AI error), **Threads** lists `GET /api/v1/conversations` with task deep-links, **Tasks** lists `GET /api/v1/tasks` with status filters and a detail page (`GET /api/v1/tasks/:id` — steps, outcome/failure, cost/quality, cancel/retry), and **Settings** handles workspace switching (every surface is workspace-scoped), shows the instance URL, and signs out. A workspace store (`WorkspaceStore`) persists the selected workspace across launches; the workspace list loads at sign-in. The empty "Agents" tab is removed — the API exposes no session-scoped agents list, so it was an empty screen by construction. New pure model-parsing tests cover the boundary's sharp edges (tz-naive timestamps, `numeric`-as-string cost, the chat `status` discriminator including the response that omits `status`). `flutter analyze` clean; 10 tests pass; the APK builds.
- **Android builds install again — the APK versionCode now advances (fixes "App not installed").** The `.pushd.yaml` build omitted `--build-number`, so `versionCode` fell back to pubspec's `+1` and **every** pushd build shipped `versionCode=1`; the retired Codemagic workflow had set `--build-number=$PROJECT_BUILD_NUMBER` (monotonic). Android refuses to install a lower `versionCode` over an already-installed app, which is the observed failure. The build now passes `--build-number` as UTC epoch **minutes** — monotonic per build and far under the 2,100,000,000 ceiling. (A stale install pinned at a higher code from the old pipeline may still need one uninstall; every build after this is installable over the last.)
- **The app mark is the Delta-Frame triangle (reverted from the Tesseract Frame).** A prior change shipped the `brand/` V2 "Tesseract Frame" across every surface; the operator prefers the open triangle with the three vertex dots, so `apps/web`'s `PlexoMark`, the `favicon.ico`, the Android launcher icons, the desktop `icon.svg`/`icon.png` + programmatic fallback + connect-screen glyph, and the Flutter `PlexoMark` are all restored to the triangle. The Tesseract-only Android adaptive icon (`mipmap-anydpi-v26` + `values/ic_launcher_background.xml`) is removed with it. `brand/` as source art is untouched; only the app surfaces revert. The unrelated install fix in `.pushd.yaml` (monotonic `--build-number`) is retained.
- **Legacy per-task `chain-resolver` deleted (LiteLLM-gateway M3 remainder).** Investigation disproved the plan's "still has live callers" note: `resolveChain` — the only entry point — had **zero production callers** (`call-model.ts` mentioned it in a comment only; `router-v2`/`routeAndCall` is the live path). The API's only use of the module was `invalidateAgentChainCache`, which busted a 60s cache that nothing ever populated. Deleted `providers/chain-resolver.ts`, `chain-resolver.ports.ts`, `chain-resolver.repository.ts`, its test, the `./providers/chain-resolver` package export, the vitest alias, and the now-dead invalidation calls in `routes/intelligence.ts`. The `routing_chains` table and its editor/dashboard reads stay (a configuration/analytics surface) — noted in `schema.ts`. `knowledge.ts`/`models_knowledge` stay: they have genuinely live callers (`syncModelKnowledge` from `cron.ts` + `routes/models.ts`; `getModelKnowledge`/`getBestReasoningModel` from `chat.ts`; `intelligence-spend`; `routing-defaults`; `router-v2/candidate.ts`). Agent suite 1455 → 1449 (the six deleted resolver tests); all other gates green.
- **Fallback indication is now uniform across every API call path, via one shared factory.** The prior PR wired `onFallbackEngaged` only in the webchat route; channels (`channel-ai.ts`), the app transport (`chat-app-transport.ts`), and the inference proxy each carried their own auth-only options, so a provider fallback there was logged (if at all) with no consistent shape. New `apps/api/src/lib/provider-fallback-opts.ts` owns the `provider_auth_error` / `provider_fallback` logging and workspace events once; all routing entry points build their `FallbackOptions` from it. No behavior change beyond the added `provider_fallback` indication on those paths.
- **A software deliverable typed into chat ("make a snake game") now actually executes and produces an artifact — on both web entry points.** The chat route had two gaps #199 did not cover. (1) The webchat LLM classifier labelled "make a snake game" `CONVERSATION`, and its verdict outranked the heuristic's `execDefault: TASK`, so no task was queued. `preClassifyIntent` now decides a self-contained software request `TASK` deterministically via `isSoftwareDeliverableRequest()` in `@plexo/domain/deliverable-verbs` (requires a deliverable verb AND a software noun, minus content nouns), so the model can never downgrade it. (2) Even when intent was `TASK`, the message took the **inline** loop, whose toolset deliberately excludes `write_asset`/`task_complete` — returning a text reply with no taskId, no artifact, and no outcome. The chat route now routes a self-contained deliverable to the async **task queue** (same path as `background: true`) so `write_asset` runs, and it skips the lossy description-synthesis call for these short, specific asks. Tests: `deliverable-verbs.test.ts`, `chat-intent.test.ts`, `chat-quality.test.ts` (new "deliverable queues" case). Verified live: `snake.html` artifact + an outcome row with a working `/s/<id>` play URL.
- **Fallbacks are now dictated by, and indicated from, the workspace provider chain.** Two changes under ADR 0012 (pre-mortem Failure 3: "preference is a hard input… degradation is logged, not hidden"). *Dictated:* `routeAndCall`'s cascade passes the workspace chain (`primary → fallbackChain`) to the selector on every **fallback** iteration, and the selector ranks by chain position first and manifest/stats score second — so a fallback follows the operator's configured order instead of the scorer silently reordering it. The first pick stays "best per task" (Q1 hybrid), so steady-state selection is unchanged. *Indicated:* `chat.ts`'s `fallbackOpts` now wires `onFallbackEngaged` — a fallback emits a structured warn log and a `provider_fallback` workspace event naming the failed primary, the provider that served the call, and the ones skipped. *Capability-aware:* a new `capability-mismatch` error class in `router-v2/error-classifier.ts` catches a model rejecting the call shape (e.g. `does not support tools`) as a specific, fall-back-next reason, so a tool-bearing call never dead-ends on a tool-less model. Tests: `equivalence.test.ts` (classifier case + two `chainPreference` selector cases).
- **The Delta-Frame mark is now the web favicon and the mobile in-app logo too.** `apps/web/src/app/favicon.ico` was still the stock Next.js placeholder — regenerated from the brand mark (triangle + three vertex dots, `#4DAAFC` on `#101520`) as a multi-size ICO (16/32/48, embedded PNG entries). The Flutter sign-in screen showed a generic `Icons.hub_outlined`; a shared `apps/mobile/lib/src/widgets/plexo_mark.dart` mirrors the web `PlexoMark` SVG geometry so the mark renders identically across web, mobile, launcher, and desktop.
- **Desktop tray/window icon was blank — `build/icon.png` was never packaged.** `electron-builder.yml`'s `files:` shipped only `src/**/*` and `package.json`, so `main.cjs`'s `createTray()` (`nativeImage.createFromPath('../build/icon.png')`) resolved to a missing file inside the app and produced an empty tray icon; `BrowserWindow` likewise set no `icon`. Fixed: `build/icon.png` is now in `files:`, `createWindow()` sets the window/taskbar icon, and both icon loads go through a `resolveIconPath()` helper with a programmatic 16×16 BGRA fallback (`nativeImage` cannot render an SVG data URL) so a missing asset can never yield a blank tray again. Verified: rebuilt the ARM64 installer, confirmed `\build\icon.png` is inside the packaged `app.asar`, installed it over the existing app (silent install needed an explicit `/D=` — the bare `/S` returned NSIS exit 1223), and the app boots with a tray. The art is also now the brand **Delta-Frame mark** (triangle + three vertex dots) instead of the old lightning bolt — `build/icon.svg`/`icon.png`, the programmatic fallback raster, and the renderer connect-screen glyph all match the Android launcher and the in-app `PlexoMark`.
- **Deliverable asks no longer get misrouted to chat and dumped as raw text (no artifact/link).** Three layers each kept their own "is this a task?" verb list and had drifted: the chat classifier knew `make`, but the executor's `detectConversationalTask()` and the agent-loop fast-path planner did not. So "make a snake game" was classified TASK at chat, queued, then **re-classified CONVERSATION by the executor**, which strips every tool — including `write_asset` — leaving the model to answer in chat and produce zero artifacts and no share/play link (confirmed in prod: task completed in 14s, 0 tool calls, 0 artifacts). Fixed by centralizing the vocabulary in `@plexo/domain/deliverable-verbs` (`hasDeliverableVerb`) and using it in all three places: the executor predicate, the fast-path synthetic plan (which now declares `write_asset` for a deliverable instead of `toolsRequired: []`), and a new pure post-planner normalizer (`normalizeDeliverableTools`) that backfills `write_asset` when the model emits a single-step deliverable plan with no tools. Tests: `deliverable-verbs.test.ts`, `detect-conversational.test.ts`, `normalize-deliverable.test.ts`. Also fixes `/agent/status` being called without `workspaceId` from chat (it always returned `currentModel: null`), and the composer's "Default (agent)" now names the resolved primary model.
- **A provider HTTP 400 no longer dead-ends the whole task (`E_UNKNOWN` on a plain "Write me a joke").** `classifyError` mapped a generic "Bad Request" to `class: 'unknown', shouldFallback: false` (`fail-hard`), so a provider-specific 4xx aborted the cascade instead of trying the next provider — the task failed outright. Added an `unknown-4xx` class (last in the chain, so auth/quota/rate-limit/context/parse keep their precise handling) that falls back to the next provider with a short cooldown. Test: `equivalence.test.ts` gains the 400 cases.
- **Android release builds could not reach any host ("Can't reach https://<instance>. Check the address and your connection" on sign-in).** The main `AndroidManifest.xml` declared no `android.permission.INTERNET`; the debug/profile variants only inherit it from Flutter tooling (hot-reload/DevTools), so the shipped APK was built with zero network access on a stock device — the host itself was healthy (verified `200`/`401` from the public host). `uses-permission android:name="android.permission.INTERNET"` is now declared in `apps/mobile/android/app/src/main/AndroidManifest.xml`, restoring sockets in release builds.
- **The Android launcher icon is the Delta-Frame mark.** The five `mipmap-*` `ic_launcher.png` assets were still the stock Flutter placeholders; each is regenerated from the brand mark (triangle with the three vertex dots, `#4DAAFC` on the `#101520` canvas), matching the desktop tray icon and the in-app `PlexoMark`.
- **Deployed `plexo-api` to the live host at `ec4ef4ce`, and made LiteLLM the operator workspace's routing provider.** The running image had been ~2 weeks stale (`23a227ae`); it now carries the first-class `litellm` provider, the deleted legacy router, the reasoning→content shunt, and the PROJECT-confirm fix. Verified on the live stack: `plexo-api` healthy, boots clean (no errors), and a real `routeAndCall('codeGeneration')` selected `litellm/auto` (manifest prior 4, ahead of groq/cerebras) and returned non-empty content from the gateway in ~860ms. The operator workspace's provider row was flipped `custom_litellm` → `litellm` (preference 0, `selected_model=auto`) and its `judgeModel` pin likewise (`custom_litellm/auto` → `litellm/auto`, fixing a pin that pointed at a now-nonexistent provider and would have forced a fail-closed 0.3 judge score). Deploy safety: confirmed the DB schema has **zero structural delta** between the stale image and main (only a comment), so the F19 un-journaled-migration hazard does not gate this deploy; `plexo-api` does not auto-migrate at boot; disk had 276G free; the prior image was tagged for rollback. Only `plexo-api` was rebuilt/recreated; web/saas untouched.
- **Chat "Create Project" confirm no longer 400s (`intent must be TASK`).** `POST /api/chat/execute-action` handled only `intent === 'TASK'`, but the chat UI's PROJECT confirm chip posts `intent: 'PROJECT'`, so clicking "Create Project" always failed with `INVALID_INTENT`. The PROJECT branch had never been implemented. It now queues a task exactly like TASK (the executor plans multi-step work itself) and returns `{ taskId }`, which the frontend already prefers over `sprintId`. A `planning` sprint was deliberately **not** created: the sprint orchestrator (`packages/agent/src/sprint`) was deleted in DD-6, so a sprint row would advance nothing — a silent no-op worse than the error. Dead bits removed with it (`sprintsRepo`/`nameProject` imports, the category/repo downgrade, `VALID_CATEGORIES`). New route test `chat-execute-action.test.ts` (4 cases: TASK, PROJECT, unknown intent, bad workspace).

- **Legacy `IntelligentRouter` deleted (LiteLLM-gateway M3, dead half).** Investigation proved `resolveModel` — the only entry point into `providers/router.ts`'s `IntelligentRouter` — had **zero production callers**: the executor's primary model path is `routeAndBuild` (router-v2), internal calls use `routeAndCall`, and `inference-client.ts` was an unimported interface doc. Legacy `proxy`-mode workspaces now route like byok (router-v2 never dispatched `handleProxy`); the managed-routing use case is the `litellm` provider + `auto` alias from M1. This is the "router-v2 parity" task resolving as *delete, not parity* for the first-party lane (ADR 0056).

### Fixed
- **`ci.yml` documented a trigger that does not exist, inviting the exact change that would hand fork code host root.** The `docker-build` job's comment claimed it "is back on `pull_request`" — true only before `95f8896`, which removed the PR triggers from every self-hosted workflow because this repo is public and the socket runner is host-root-equivalent. The comment was left behind and reads as a spec, so the next contributor could "restore" a PR trigger on a job that mounts `/var/run/docker.sock`. The comment now states the invariant (never bind `pull_request`/`pull_request_target` to a `self-hosted` runner here; PR-triggered workflows stay on GitHub-hosted, per `changelog-check.yml`) and keeps the `#161` history for why the trigger is push-only. Comment-only: triggers are still `push` alone and `runs-on` is unchanged.
- **The public repo claimed MIT and described a copyleft obligation it cannot satisfy.** Plexo was relicensed AGPL-3.0 → MIT in `7dcd02dd` and `apps/gmessages` was deleted in `716234ed`, but `LICENSING.md` still asserted that the subtree was AGPL-3.0-only, linked `apps/gmessages/LICENSE` (a path that no longer exists), claimed the copyleft extended to the linked work, and walked readers through AGPL Section 13 network-disclosure obligations for a component that is not in the tree. `README.md` and `CONTRIBUTING.md` repeated the carve-out, and `apps/api/openapi.yaml` was the sharpest case: `license: name: MIT` paired with `url: https://www.gnu.org/licenses/agpl-3.0.html` — a machine-readable contradiction that API consumers ingest, so a client library could report the wrong license to its users. The URL now points at `opensource.org/licenses/MIT`. `LICENSING.md` is rewritten as plainly MIT with no carve-out, keeping the do-not-introduce-copyleft rule (still load-bearing — arguably more so, now there is no carve-out to appeal to) and expanding it, and recording the former subtree as removed rather than deleting the fact: a reader who finds an old release needs to know it existed and that any future AGPL component belongs in a separate repo or subtree with its own `LICENSE`. `CLAUDE.md` also dropped the deleted Go gmessages sidecar from its language/runtime and server stack lines, so an agent asked about the stack no longer looks for an app that is gone. Runtime references to an *optional external* gmessages sidecar (`GMESSAGES_SIDECAR_URL`, `packages/db/src/gmessages-schema.ts`, compose wiring) are deliberately untouched — those describe a connector an operator may run, not a deleted in-repo app. `CHANGELOG.md`/`MIGRATING.md` history left as written. `AGENTS.md` carries no AGPL or gmessages text, so the generated provider mirrors need no regen; `sync-agents.sh --check` passes unchanged. Note: line 44 below cites the deletion as `282e1f5`, which does not resolve in this repository — the resolvable commit is `716234ed`; left as written since it is a historical entry, but worth a look separately.
- **The graphiti sidecar image could not be built, and — separately — could not boot. Both were invisible.** The upstream watcher had failed on every daily run since 2026-08-30 with `"/services/graphiti-sidecar": not found`: it passed the service directory as the Docker build context while the Dockerfile `COPY`s `services/graphiti-sidecar/...`, which needs the repo root (`docker/compose.yml` gets this right, so only the workflow was wrong). Fixing that exposed the real breakage underneath. The sidecar pins its direct dependencies but nothing bounds *their* dependencies, and two upstream releases had landed: `openai` 3.x moved its HTTP layer to the `httpx2` distribution while `graphiti-core` still does `import httpx`, so a fresh image died on boot with `ModuleNotFoundError: No module named 'httpx'`; and `redis` 8.x changed the constructor `falkordb` calls, so the first episode write raised `TypeError: Redis.__init__() got an unexpected keyword argument 'himport_registry'`. Nothing in this repo changed to cause either; production kept serving only because its running image predates them. Both are now pinned (`openai==2.54.0`, `redis==7.4.1`) with the reasoning recorded next to the pins.
- **`graphiti-core` bumped 0.29.0 → 0.29.3**, verified by ingesting and searching against a real FalkorDB rather than by a green TypeScript run. The vendored `redisearch_groupid_patch.py` is deleted with it: it monkey-patched `graphiti-core`'s RediSearch fulltext builder to backslash-escape hyphenated-UUID `group_id`s (without which `/v1/search` 500'd on every workspace), upstream landed that fix in 0.29.2 (getzep/graphiti#1549), and on the new pin the wrapper was verified byte-for-byte redundant — patched and unpatched builders emit the identical escaped query. Its own docstring said to remove it when upstream fixed it. Keeping it meant keeping a module that reaches into vendored internals and raises on boot if they move.
- **The schema-compat probe was Kuzu-era and could never have run.** It restored a tarball of production's Kuzu database over SSH — Kuzu was replaced by FalkorDB in ADR 0010, the workflow's snapshot step still carried literal `<prod-server-ip>` placeholders, and the `VPS_SSH_KEY` secret it wanted does not exist. Its stub also demanded an HMAC signature on the inference calls, while the sidecar's LLM and embedder calls go out through graphiti-core's OpenAI clients, which can only send `Authorization: Bearer` — so every inference call would have 401'd. Replaced by `services/graphiti-sidecar/test/probe.sh`, which needs no production data and no deploy key.

- **The 47 pre-existing `@plexo/web` lint warnings are cleared, and the web lint gate is now `--max-warnings 0`.** ESLint `@typescript-eslint/no-unused-vars` now honors a leading-underscore convention (`argsIgnorePattern`/`varsIgnorePattern`/`caughtErrorsIgnorePattern`/`destructuredArrayIgnorePattern` = `^_`), which retired the intentional `_`-prefixed placeholders; every genuinely dead import/local/const was deleted. `react-hooks/exhaustive-deps`: `sprints`/`tasks` in `tasks/page.tsx` are wrapped in `useMemo` so their downstream memos/effects stop re-running each render; `handleRuleDelete` in `agents/page.tsx` gained its real `confirmAction` dep; the mount/poll effects in `repo-picker.tsx` and `parallel-status-panel.tsx` and the write-driven reloads in `artifact-workbench.tsx`/`code-mode-shell.tsx` (whose stale `eslint-disable` directives sat one line above the deps array and suppressed nothing) got correctly-placed, commented intentional-omit directives. Two `<img>` (a `data:` paste thumbnail in `quick-send.tsx`, small decorative marquee logos in `page.tsx`) carry documented `no-img-element` disables — `next/image` cannot optimize a data URL and would churn the public-route visual baseline. `command-palette.tsx`'s option buttons gained `role="option"` so `aria-selected` is valid; `stabilization/dashboard.tsx`'s ternary-as-statement became an `if/else`. The `--max-warnings 0` flag on the web lint script keeps them from creeping back — the same ratchet as every other gate. Note: `quick-send.tsx` had a doubly-dead "View task" link (`status` was never set to `'sent'` and `setTaskId` was never called); the unreachable state + block were removed and the missing wiring flagged separately.

### Added
- **`arch:check` now looks at `packages/session-fabric` and the six `extensions/core/*` bridges.** It had only ever been pointed at ten source trees, so those seven were never cruised — a violation in them could not be counted, baselined, or burned down, because nothing looked. Widening the scan costs nothing: 795 modules / 2524 dependencies now, up from 781 / 2483, with the ratchet unmoved at 32. The scan path alone would have bought almost nothing, though, since no rule targeted `packages/session-fabric/src` — so it also adds a `session-fabric-imports-outer` rule (additive; no existing rule body touched) asserting what `clean-architecture.md` already claims about that package: framework-free runner policy, no ORM, no HTTP framework, no vendor SDK, no outer package. Proven as a tripwire rather than assumed — planting `import { sql } from 'drizzle-orm'` in `session-fabric/src/policy.ts` fails the gate by name, and reverting restores green. The bridges keep global-rule coverage only: they are edge adapters and legitimately import vendor SDKs, so a layering rule for them would be wrong; what they gain is cycle detection.
